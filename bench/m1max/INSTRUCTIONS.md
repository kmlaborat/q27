# q27 Metal / M1 Max 32GB チューニング指示書

(ユーザー指示書 — 2026-09-23 貼り付け原文。進行判断に迷ったらこれを当たる。
以降の口頭/amend: クロスオーバーグリッド・Toolchain DL・正しさ基準づくりの3件承認済み。
グリッドは試行あたりタイムアウト必須。matvec改造前に正しさ基準完了が必須。
attention_f16のオーバーヘッド切り分けをmatvec解析と並行で軽くやること、が追記指示。)

対象: q27 (Qwen3.8-27B, q4sティア) の Apple Silicon Metal バックエンド
実機: M1 Max 32GB Mac Studio (統一メモリ帯域 実測 rws=26.0 GiB, 理論帯域 400GB/s)

## 最優先タスク: DeltaNet occupancy バグの修正

### 現象
`metal_backend.mm:2437` / `2626` で以下がthrowされ、生成が全滅する:
```
q27 Metal: unsupported DeltaNet shape
```
原因: `impl_->delta.maxTotalThreadsPerThreadgroup < 512` というガード。DeltaNet(GDN再帰)カーネルのコンパイル後occupancyがM1 Max(Apple7世代GPU)では512スレッドに届いていない。M4(Apple9世代)前提で設定された閾値と推測される。validate-onlyは通過するが、chunk prefill・serial stepの両経路で生成が止まる。

### 手順(この順序で進めること。いきなり閾値の書き換えだけで済ませない)

1. **診断: なぜ512を切るのか特定する**
   - `MTLComputePipelineState.maxTotalThreadsPerThreadgroup` を、このデバイス(M1 Max)で当該DeltaNetカーネルについて実際にクエリし、返ってくる数値をログに残す
   - 原因の切り分け:
     a. threadgroup共有メモリの使用量がM1 MaxのSM当たり割当を超えている
     b. レジスタ使用量が多く、512スレッド分のレジスタがM1 Maxのコアで確保できない
     c. Apple7世代の物理的な上限で、そもそも512は狙えない
   - Xcodeインストール前でも分かる範囲(a/bの可能性の当たりをコード上のスレッドグループメモリ確保量・ループアンロール量から推測する等)で仮説をコード内コメントとして残す。Instrumentsでの厳密な確認はXcode導入後(フェーズ2)で構わない

2. **修正: 既存の256スレッド版フォールバックに切り替える**
   - コード上に256スレッド版のパスが既に用意されている想定。まずはこちらへの切り替えを最優先で行う
   - 512維持のためのレジスタ/共有メモリ削減は、動作確認が取れた後の余力があれば取り組む(優先度は低)

3. **検証(これを飛ばして次工程に進まない)**
   - validate-onlyだけでなく、実際に数トークンの生成が通ることを確認する
   - 256スレッド版と512スレッド版(手元でテスト可能な環境があれば、あるいは既存のCPU/他バックエンドの参照出力があれば)とで、同一プロンプトに対するlogitまたは出力トークン列に差異がないことを確認する。数値的に同一の結果になるはずなので、差異があれば実装ミスを疑う

修正が完了し、上記2点の検証が通った時点で報告すること。

## フェーズ1: ベースライン計測(DeltaNet修正後に着手)

1. `tools/bench_metal.cpp` を使い、以下の条件でベンチマークを実施:
   - pp(プロンプト処理)とtg(トークン生成)を分離して計測
   - コンテキスト長: 短い条件(512程度)と長い条件(4096〜8192程度)の両方
   - 各条件3回以上実行し、中央値を記録
2. `powermetrics` はsudo権限が必要なため、ユーザー側が別ターミナルで以下を手動実行する(NOPASSWD設定は現時点では行わない):
   ```
   sudo powermetrics --samplers gpu_power,cpu_power,memory -i 1000
   ```
   ベンチ実行と並走させ、GPU使用率・電力・メモリ帯域相当の指標を記録する
3. モデルロード時の実メモリ使用量(internal/compressed含む)をベンチ内に既に組み込み済みの記録機能で取得し、GPUの `recommendedMaxWorkingSetSize` に対する余裕/逼迫を把握する

## フェーズ2: プロファイリング(Xcode導入後)

- `brew install --cask xcode` はバックグラウンドで早めに開始しておく(数十GB、時間がかかるため)
- Xcode Instruments の Metal System Trace(または `xctrace` CLI)で、tg実行中の1トークン分をキャプチャ
- GPUタイムライン上でどのカーネル(Attention層・FFN層・DeltaNet/GDN層のいずれか)が最も時間を占めているかを特定する
- 併せて、DeltaNetカーネルのレジスタ/共有メモリ使用量をコンパイラ出力から確認し、フェーズ0で立てた仮説(a/b/c)を裏付ける

## フェーズ3: 正しさ基準づくり(カーネルを本格的に変更する前に必須)

- 固定プロンプト数十件に対する出力(またはlogit上位k件)を保存し、以降の変更のたびに一致率を機械的にチェックできる仕組みを用意する
- wikitext等でのPPL(パープレキシティ)の現状値を記録しておく

## 進行ルール

- 各フェーズの完了時点で、数値・ログ・仮説をまとめて報告すること
- カーネル変更を伴う修正は、必ず動作確認(生成が通る)と出力の数値的な一致確認をセットで行ってから次に進むこと
- 速度最適化より先に「正しく動く」ことを優先する
